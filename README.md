# SKYNET — ИИ-институт

Мультиагентная система на CrewAI: головной диспетчер направляет запрос
в нужный отдел, а отдел выполняет предсказуемый конвейер задач с проверкой
качества и самообучением на собственном опыте.

## SKYNET 0.2

Версия 0.2 усиливает проект как платформу:

- добавлен отдел контроля качества `quality_control_dept`;
- роутер получил keyword-fallback и JSON-классификацию;
- Docker-деплой сгенерированных агентов больше не передаёт весь `.env`
  контейнеру, а использует whitelist переменных окружения;
- добавлены лимиты CPU/RAM и управляемый network mode для контейнеров;
- добавлены базовые тесты и GitHub Actions CI;
- пошаговый план развития вынесен в `docs/SKYNET_0.2_ROADMAP.md`.
- режимы `local/cloud/hybrid` описаны в `docs/RUNTIME_MODES.md`;
- сценарий "Claude Pro без API" описан в `docs/CLAUDE_PRO_NO_API.md`;
- единая архитектура ролей, лимитов и истории запусков описана в
  `docs/AGENT_ARCHITECTURE.md`.

Включить контроль качества перед финальной выдачей:

```bash
ENABLE_QUALITY_GATE=1 python run.py "напиши пост в соцсети про запуск нового тарифа"
```

## Структура

```
run.py              — точка входа в институт целиком (диспетчер выбирает отдел)
main.py             — прямой запуск отдела Кодеров, минуя диспетчер
src/institute/       — диспетчер + общие инструменты самообучения
src/agent_factory/   — отдел "Кодеры"
src/marketing_dept/  — отдел "Маркетинг + Копирайтеры"
src/design_dept/     — отдел "Дизайнеры"
src/quality_control_dept/ — отдел контроля качества
knowledge/            — локальная база уроков каждого отдела (самообучение)
references/           — сюда кладёте скриншоты-референсы для отдела Дизайнеров
generated_designs/    — сюда отдел Дизайнеров сохраняет design-system.md и index.html
```

## Отделы

### Кодеры (`src/agent_factory`)
Проектирует, пишет, проверяет и деплоит **новых** CrewAI-агентов по запросу.
- **Архитектор** — превращает запрос в спецификацию.
- **Исследователь** — ищет практики/инструменты/примеры.
- **Кодер (LLM-инженер)** — пишет итоговый Python-код агента.
- **Ревьюер/QA** — проверяет синтаксис, безопасность, соответствие спецификации.
- **DevOps** — при вердикте APPROVED сам собирает и запускает Docker-контейнер
  (`docker build` + `docker run`) сгенерированного агента.
- **Аналитик самообучения** — после каждого запуска сохраняет 1-3 урока
  в `knowledge/coders_lessons.md`.

### Маркетинг + Копирайтеры (`src/marketing_dept`)
Пишет маркетинговые/рекламные тексты по запросу.
- **Маркетинг-стратег** — составляет бриф (аудитория/УТП/тон/канал).
- **Копирайтер** — пишет текст по брифу.
- **SEO-специалист** — добавляет ключевые слова/meta, если канал поисковый.
- **Редактор** — финальная вычитка на соответствие брифу.
- **Аналитик самообучения** — сохраняет уроки в `knowledge/marketing_lessons.md`.

### Дизайнеры (`src/design_dept`)
Собирает готовый HTML/CSS-макет сайта/лендинга по референсам (скриншоты
с Pinterest/Dribbble/Awwwards/Godly и т.п.), без генерации картинок —
только реальный код, который открывается в браузере.
- **Аналитик референсов** — смотрит на картинки из `references/` через
  vision-запрос к Claude (типографика/сетка/палитра/ритм/пространство).
- **Архитектор дизайн-системы** — сводит разбор в одну согласованную
  систему, сохраняет `design-system.md`.
- **Вёрстальщик** — пишет `index.html` с инлайн-CSS по дизайн-системе;
  если в запросе указано "чего нет" (цены/отзывы/фото/цифры) — ставит
  текстовые заглушки, не выдумывает факты.
- **Ревьюер дизайна** — сверяет с ограничениями и дизайн-системой.
- **Аналитик самообучения** — сохраняет уроки в `knowledge/design_lessons.md`.

**Как использовать:** сохраните скриншоты-референсы в `references/`,
затем запрос по шаблону:
```
python run.py "Создай лендинг для фитнес-студии — аудитория новички 25-40 лет.
Референсы: @references/. 1. В №1 нравится минимализм и крупная типографика.
2. В №2 — контраст чёрного и лаймового. Стиль: тёмный фон, дерзкое настроение.
Главный приём — крупный акцентный заголовок на весь экран.
Ограничения: мало текста, много воздуха, каждая секция визуально не похожа
на предыдущую. Чего нет: цены, отзывы, цифры — заглушки, не выдумывать."
```
Результат — `generated_designs/<project>/design-system.md` и `index.html`.

### Планируется
Продажники, Безопасники — добавляются по той же схеме: свой `crew.py` +
`config/{agents,tasks}.yaml`, регистрация в `src/institute/registry.py`.

## Самообучение

Два независимых механизма, оба полностью локальные (без внешних сервисов):

1. **Локальная база уроков** — отделы сохраняют проверенные наблюдения в
   `knowledge/<отдел>_lessons.md`, без внешнего сервиса.
2. **Рефлексия** — отдельный агент "Аналитик самообучения" в конце каждого
   запуска извлекает 1-3 конкретных урока и дописывает их в
   `knowledge/<отдел>_lessons.md` через инструмент `record_lesson`
   ([learning_tools.py](src/institute/learning_tools.py)). Этот файл
   подключён каждому отделу как `knowledge_sources` — все агенты отдела
   используют накопленные уроки в следующих запусках, когда подключён
   совместимый knowledge source.

CrewAI memory (`ENABLE_CREW_MEMORY=1`) включается отдельно. В локальном режиме
по умолчанию она выключена, чтобы не требовать embeddings или API-провайдера.

Посмотреть, чему научился отдел: открыть `knowledge/coders_lessons.md`
или `knowledge/marketing_lessons.md` — обычный markdown, редактируется
вручную при необходимости (например, чтобы удалить неверный урок).

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -e .
cp .env.example .env   # local-режим работает без ключей
ollama pull llama3.1:8b

# Для cloud/hybrid с облачными моделями ключи добавляются отдельно:
# ANTHROPIC_API_KEY=... или OPENAI_API_KEY=...

# Через диспетчер института — сам определит отдел:
python run.py "напиши пост в соцсети про запуск нового тарифа"
python run.py "агент, который мониторит RSS-ленты и шлёт саммари в Telegram"

# Напрямую в отдел Кодеров, минуя диспетчер:
python main.py "агент, который парсит прайс-листы поставщиков в единый Excel"
```

Отдел Кодеров дополнительно сохраняет сгенерированный `agent.py` в
`./generated_agents/` инструментом `save_generated_agent`.

## Модели

Каждая роль каждого отдела использует свою LLM (см. `.env.example`),
задаётся переменными окружения `<ОТДЕЛ>_<РОЛЬ>_MODEL` в формате
`provider/model` — без правки кода. Диспетчер института использует
дешёвую модель (`ROUTER_MODEL`, по умолчанию Haiku) — классификация
отдела не требует мощной модели.

В `local` режиме роли используют Ollama через LiteLLM и `OLLAMA_API_BASE`.
Установить дополнительный API-ключ для этого режима не требуется.

## Деплой в облако

```bash
docker build -t agent-factory .
docker run --rm -it \
  -e ANTHROPIC_API_KEY=... \
  -e OPENAI_API_KEY=... \
  -v $(pwd)/generated_agents:/app/generated_agents \
  -v $(pwd)/knowledge:/app/knowledge \
  agent-factory "агент, который парсит прайс-листы поставщиков в единый Excel"
```

## ⚠️ Автономный деплой (отдел Кодеров)

DevOps-агент **сам** выполняет `docker build` и `docker run -d` на хосте,
где запущен институт — без запроса подтверждения на каждый запуск. Это
осознанный выбор архитектуры, но учитывайте: любой успешно прошедший
ревью сгенерированный агент реально запустится контейнером на этой
машине/сервере. Убедитесь, что:
- Docker на хосте доступен только доверенным пользователям;
- `.env` не содержит лишних секретов, которые не должны попасть в
  контейнер сгенерированного агента (передаётся целиком через `--env-file`);
- есть лимиты на ресурсы/количество контейнеров при частой генерации.

### Гвард на деплой — Python, а не обещание LLM

Раньше DevOps-агент получал вердикт Ревьюера текстом и должен был сам
решить, деплоить или нет — модель могла ошибиться или проигнорировать
инструкцию. Теперь:
1. `review_code_task` возвращает **структурированный** (`output_pydantic`)
   вердикт — [ReviewVerdict](src/agent_factory/models.py) с полем
   `verdict: Literal["APPROVED", "CHANGES_REQUESTED"]`.
2. `callback` на этой задаче пишет вердикт в файл (`.state/last_review_verdict.json`,
   см. [state.py](src/agent_factory/state.py)) — независимо от того, что скажет DevOps-агент.
3. Инструмент [deploy_generated_agent](src/agent_factory/tools/deploy_tools.py)
   САМ читает этот файл в начале своей работы и физически отказывается
   вызывать `docker build`/`docker run`, если вердикт не APPROVED —
   этот шаг нельзя обойти уговорами модели.

Состояние сбрасывается перед каждым новым запуском отдела (`@before_kickoff`),
чтобы вердикт из прошлого прогона не "утёк" в следующий.

## Трассировка и оценка качества

- **Трассировка** — каждый отдел пишет JSON-лог по каждой выполненной
  задаче в `traces/<отдел>_<дата>.jsonl` ([tracing.py](src/institute/tracing.py)) —
  локально, без сторонних сервисов. Формат — одна JSON-строка на задачу
  (время, агент, превью результата), можно читать как обычный текстовый лог.
- **LLM-as-Judge** — перед тем как "Аналитик самообучения" сформулирует
  урок, он вызывает [judge_final_output](src/institute/eval_tools.py) —
  независимый вызов модели, который оценивает итоговый результат отдела
  по шкале 1-5. Это не даёт самообучению слепо закреплять уроки на основе
  собственного мнения того же агента, который делал работу.

## Исполнение конвейера

Отделы используют `Process.sequential`: каждый `Task` получает контекст только
от предыдущих явно указанных задач из `config/tasks.yaml`. Это снижает число
лишних вызовов модели, делает локальный запуск воспроизводимее и упрощает
расширение отдела. Общая политика ограничений находится в
`src/institute/runtime.py`, а история каждого прогона — в `runs/`.
